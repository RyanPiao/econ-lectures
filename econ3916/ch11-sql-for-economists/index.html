1  •  You Already Know This

Six operations, ten chapters of practice, and a new spelling.

Not an Analogy — a Shared Ancestor

You have spent ten chapters filtering rows, selecting columns, grouping, aggregating, sorting and merging. Those six operations are essentially all of SQL.

In 1970 Edgar Codd proposed organising data into relations — tables — manipulated by a small formal algebra. SQL was built directly on it. Pandas was built four decades later, by people who had spent their careers using SQL.

pandas is procedural

You give the steps. Filter, then group, then take the mean. Each step makes an object you could inspect. A recipe.

SQL is declarative

You describe the table you want. The engine decides how to make it — often in a different order than you wrote, chosen for speed.

You are learning notation, not concepts. That is why this takes days rather than months.

3 min. Ask who has written SQL before — usually a third of the room from an internship — then reassure the rest explicitly: no prior SQL is assumed and every keyword today gets introduced before it is used. The Codd point matters because it tells them the translation table on the next slides is exact, not a rough correspondence.

The Order You Write It Is Not the Order It Runs

FROM runs first — you cannot filter a table you have not named.

WHERE runs before GROUP BY. So WHERE cannot reference an average — at the moment it runs, no averages exist yet.

That is what HAVING is for. “WHERE vs HAVING” is the most common entry-level SQL interview question there is, and the answer is not that one is better.

It is that they run at different times.

3 min. Draw the two ladders on the board yourself rather than only showing the figure — the crossing arrows are worth the thirty seconds. Tell them plainly this is on interviews; students remember things they know will be tested outside the room.

Both Clauses, Doing Different Work

Which categories earned more than \$10,000 since December 2025?

SELECT category, SUM(revenue) AS rev
FROM sales
WHERE  month >= '2025-12'
GROUP BY category
HAVING SUM(revenue) > 10000
ORDER BY category
category |   rev
---------+---------
books    | 12000.0
coffee   | 13000.0

WHERE removes November before any summing. Without it, books total \$16,000 and the answer silently covers the wrong period.

HAVING drops tools (\$3,500) after grouping — which WHERE could not do, because at that point no total existed.

3 min. Walk the query in execution order, not reading order: FROM sales, then WHERE, then GROUP BY, then HAVING, then SELECT. Say the numbers out loud — books would have been sixteen thousand without the WHERE, and that is a wrong answer that looks completely fine.

Poll: Why Can't WHERE See an Average?

SELECT dept, AVG(pay) FROM staff
WHERE AVG(pay) > 50000 GROUP BY dept   -- BinderException

Why does this fail?

A) AVG is misspelled — SQL wants MEAN
B) WHERE runs before GROUP BY, so no average exists yet
C) You can never filter on an average in SQL
D) WHERE needs the column listed in SELECT first
1 min. Students click to vote on their devices; results appear on the next slide. This is the easiest poll of the day and that is deliberate — it is the first one, and you want everyone to discover the mechanics works before Poll 2, which is the one that matters.

Answer: B — It Is a Question of Timing

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. When WHERE runs, the rows have not been grouped, so there is nothing to average. Move the condition to HAVING and it works.

Why C is the tempting wrong answer: you absolutely can filter on an average. You just have to do it after the aggregation exists — which is the entire job description of HAVING.

First: Where Is the Database?

There isn't one.

duckdb.sql("SELECT ... FROM customers") reads the name customers out of your Python namespace — the same variable you built one line ago with pd.DataFrame(...) — and runs the query against that DataFrame, in memory.

No server. No connection string. No CREATE TABLE. No file on disk. DuckDB is a SQL engine you imported, not a database you connected to.

The table name in the query is the Python variable name. Rename the variable and the query breaks: Table with name customers does not exist.

.df() on the end converts the answer back into a DataFrame. Without it you get a DuckDB relation — prints nicely, but has no .groupby() or .iloc.

Everything you write is real, portable SQL. The same text runs against Postgres, Snowflake or BigQuery — with the table names pointing at real tables instead of your notebook's variables.

2 min, and do not skip it. This is the question every student in the room is about to have and almost none will ask. If you show a query against `customers` without answering it, a reasonable person concludes there is a hidden database somewhere, or that `customers` is a magic string, and they spend the rest of the lecture quietly confused about the wrong thing. Say the sentence "the table name is the variable name" out loud twice.

2  •  Joins, and the Cardinality Trap

The section this chapter exists for.

Join Anatomy — Four Pieces, One Line

FROM customers c LEFT JOIN region_targets t ON c.region = t.region

is exactly customers.merge(region_targets, on="region", how="left")

customers c — alias. A nickname for the table, declared just by writing it. Now you say c.revenue. Pure convenience — until two tables share a column name, which is exactly what a join key is.

LEFT JOIN region_targets t — the second table, aliased t.

ON c.region = t.region — the join key. The column that must match for two rows to be glued together. Name the wrong column and you get a wrong answer, not an error.

LEFT — keep every left row even with no match, filling the right side with NULL. That is how="left". Plain JOIN keeps only matched rows.

3 min, and take the full three. The chapter introduces this syntax inside the fanout example, which asks students with no SQL to learn alias notation and reason about cardinality in the same breath. Separate them. Point at each of the four pieces on screen as you name it. The "wrong answer, not an error" line on the join key is worth repeating.

Four rows in, four rows out. region_targets has exactly one row per region, so nothing was duplicated.

Hold on to that sentence. The next slides are what happens when it is not true.

2 min. This slide exists so that the students' mental model of "join" is set correctly before it is broken. Say explicitly: this is the join everyone has in their head, and it is only safe because of a property of the right-hand table, not a property of the word LEFT.

The Four Join Types — Read the Right-Hand Column

TypeKeepsRow count
INNER JOINOnly rows matching in both tablesCan shrink or grow
LEFT JOINAll left rows; NULL where no match≥ left table's rows
RIGHT JOINAll right rows≥ right table's rows
FULL OUTER JOINEverything from both≥ both

Almost everyone believes a LEFT JOIN preserves the left table's row count. It preserves those rows as a minimum.

A LEFT JOIN from a 1,000-row customer table to a 5,000-row order table returns between 1,000 and 5,000 rows — and which one depends entirely on the cardinality of the relationship. That is a fact about your data, not about your query.

2 min. Do not dwell on RIGHT and FULL OUTER — name them and move on; they are the first thing to cut if you are running long. The greater-than-or-equal signs are the whole slide. Ask the room whether anyone has ever checked the row count after a merge in pandas. Usually silence, which is the point.

Key Concept: A Join Has a Grain, and You Must Know It

The grain of a table is what one row represents: one customer, one customer-month, one order, one country-year.

Every join either preserves the grain or changes it. The habit is two sentences and one COUNT(*):

Before you write it. State the grain of both inputs and the grain you intend the output to have.

After you run it. Check the row count against that intention.

This single habit prevents the most consequential class of silent data error in applied work.

2 min. "Grain" is the vocabulary word of the day — write it on the board and leave it. Give them a phrasing they can actually use in a meeting: "what does one row of this represent?" It is a question that makes a senior analyst take you seriously and it costs nothing to ask.

Fanout — and Nothing Warned You

The join did exactly what you asked. The bug is in what you do next: compute a statistic as though each row were an independent customer.

It is dangerous rather than annoying because it is invisible. The table looks like customers. The IDs are real. The revenue is real. No missing data, no error, no warning.

The only symptom is that there are more rows than there should be — and nobody counts rows.

2 min. Anticipate the objection "wouldn't you notice four thousand rows?" and answer it directly: not when the join is step three of eleven in a pipeline you inherited from someone who left, and not when you never printed the shape.

The Same Chapter 8 Test, Run Twice

Correct (1 row/cust)   n =   600   diff = 11.31   SE = 9.35   t = 1.21   p = 0.2270
Fanned out (1/order)   n = 4,033   diff = 12.30   SE = 3.57   t = 3.44   p = 0.0006
3 min. Reveal one line at a time. Read them side by side out loud. Then stop talking for a beat — the inversion from p = 0.23 to p = 0.0006 is the moment the lecture lands, and it needs silence around it. Say the four-word summary: same customers, one join.

Nothing Went Wrong. That Is the Problem.

$\text{SE} \propto \sigma/\sqrt{n}$

In words: the standard error divides by the square root of the sample size. Multiply the rows by 6.72 and the SE shrinks by $\sqrt{6.72} \approx 2.6$ — exactly the factor you see.

$t = \bar{d} \,/\, \text{SE}$

In words: the $t$-statistic is the difference divided by the standard error. The difference did not move. The denominator shrank. So $t$ inflated on its own.

The $t$-test did nothing wrong. The SE formula did nothing wrong. $n$ was a lie.

 And this is error family #1 from the benchmark audit in the hook — the one-to-many join that is never re-aggregated.

2 min. Point back at the sigma-over-root-n from retrieval practice; this is the payoff for having written it on the board forty minutes ago. Naming it as error family #1 pays the hook off in the middle of the lecture rather than only at the end — the hook then earns interest twice.

The Fix: Aggregate Before You Join

A common table expression is nothing more exotic than naming an intermediate DataFrame — which you have done in pandas since Lab 1.

WITH order_counts AS (        -- name it
    SELECT customer_id, COUNT(*) AS n_orders
    FROM orders
    GROUP BY customer_id      -- ONE row per customer
)
SELECT c.customer_id, c.region,
       c.revenue, oc.n_orders
FROM customers c
LEFT JOIN order_counts oc
       ON c.customer_id = oc.customer_id
Rows after
aggregate-then-join: 600

The WITH block collapses orders to one row per customer first. The join then cannot fan out, because there is exactly one matching row.

The grain is preserved by construction rather than by luck.

4 min. Frame WITH as "assign a name to an intermediate result, then use the name" and students find it immediately intuitive — it is the same move as `tmp = df.groupby(...)`. Read the CTE bottom-up if anyone looks lost: what does the final SELECT need? One row per customer. Where does that come from? The block above.

Common Misconception

“SELECT DISTINCT fixes duplicate rows.”

It removes them from your output while leaving the cause in place — and it silently hides information.

If two of a customer's rows differ in any column — an order date, an order ID — DISTINCT keeps both. You still have fanout.

And when it does collapse rows, it destroys the evidence that anything went wrong.

Diagnose the cardinality. Do not paper over it.

1 min. This is also the standard weak answer to a common interview question, so the habit is worth forming for reasons beyond correctness. If you are running long, this is the third thing to cut — it survives in the lab.

3  •  Aggregating Without Collapsing

The single highest-value piece of SQL for an economist.

GROUP BY Collapses. Sometimes You Need It Not To.

Ten years of data for one country become one row containing the average. Usually what you want. Sometimes exactly what you do not want.

A panel of countries and years. You need each country's GDP growth: this year's GDP minus last year's, within country.

GROUP BY cannot do it — you want to keep every country-year row and merely attach a new column to it.

In pandas you already know the move:

df["prev_gdp"] = df.groupby("country")["gdp"].shift(1)

groupby(...).shift(1) does not collapse. It computes within groups and returns something the same length as the input.

2 min. Lead with the pandas line they already know and write the SQL underneath it on the next slide. Panel data is what economists work with, so say plainly that this section is the highest-return five minutes of the chapter for anyone doing empirical work.

The Same Idea, Term by Term

df.groupby("country")["gdp"].shift(1)

LAG(gdp) OVER (PARTITION BY country ORDER BY year)

OVER (...) is what turns an ordinary aggregate into a window function. SUM, AVG, COUNT, MIN, MAX all take it. Rows in, same rows out, extra columns.

PARTITION BY country is groupby("country"). Omit it and the window is the entire table.

ORDER BY year inside the OVER (...) tells the database what “previous” means. Pandas takes this from the DataFrame's row order — a source of quiet bugs. SQL makes you say it.

That inner ORDER BY is unrelated to the query's own ORDER BY at the bottom, which only controls how the output prints.

3 min. Point at each term as you say its pandas equivalent. The ORDER-BY-inside-OVER point is worth an extra sentence: pandas silently trusts the row order of your DataFrame, and if you ever sorted it differently upstream your lags are wrong with no error. SQL forcing you to declare it is a feature, not ceremony.

The Window Functions Worth Knowing

FunctionDoespandas analogue
LAG(x, k)Value $k$ rows back within the partitiongroupby().shift(k)
LEAD(x, k)Value $k$ rows forwardgroupby().shift(-k)
ROW_NUMBER()1, 2, 3 … within partition; never tiesgroupby().cumcount() + 1
RANK() / DENSE_RANK()Rank, with / without gaps after tiesgroupby().rank()

On ties: RANK() gives the same number then skips (1, 2, 2, 4). DENSE_RANK() ties without skipping (1, 2, 2, 3). ROW_NUMBER() never ties and breaks them arbitrarily (1, 2, 3, 4).

2 min. Nearly every panel operation an economist performs is on this table: growth rates, lags, leads, running totals, ranks within group, "most recent observation per unit". Say that sentence — it converts this from a syntax list into a reason to care.

Poll: What Does LAG Give the First Row?

Answer: C — NULL, and That Is a Feature

There is no earlier row in the partition, so LAG has nothing to return and says so. This propagates — the 2019 growth rate is NULL too. Pandas does the same thing when shift(1) produces NaN in the first row of each group.

Why A is the dangerous wrong answer: if LAG returned 0, the 2019 growth rate would compute as an infinite jump from nothing — and it would be a number rather than an obvious hole. NULL is SQL refusing to guess. That refusal is the subject of the next section.

Think Like an Economist: Provenance

Lars Vilhuber, the American Economic Association's Data Editor, has written about why computational reproducibility in economics fails. A recurring cause is not fraud or carelessness but provenance.

An analysis built on final_data_v3_USE_THIS.csv sitting on one laptop, produced by cleaning steps nobody wrote down.

A query against a versioned, immutable source is different in kind: the transformation is the code, the code is in git, and anyone can re-run it against the same bytes.

If you were hit by a bus, could a colleague reproduce your headline number from your repository alone? If the honest answer involves a file on your Desktop, you have a provenance problem.

1 min. Keep it short and let the file name do the work — every student recognises `final_data_v3_USE_THIS.csv` and several of them have one open right now. Connect it forward: this is why the capstone requires a repository, not a folder.

4  •  NULL Is Not a Value

Defensible, standard, and responsible for more silent errors than any other feature of the language.

Three Truth Values, Not Two

In Python

None == None

True

In SQL

NULL = NULL

NULL

The reasoning is sound. NULL means unknown, and two unknowns are not necessarily the same unknown. Asking whether one unknown equals another honestly returns “unknown”.

So SQL has three truth values — true, false, unknown — and a WHERE clause keeps only rows where the condition is true. Rows evaluating to unknown are discarded exactly as if they were false.

That last sentence is where the money goes missing.

2 min. Draw the three-valued truth table on the board — true, false, unknown — and show that WHERE keeps only true. Then go straight to the poll; do not preview the answer.

Poll: The Filter That Eats Your Data

An orders table has 8 rows. Exactly 2 have status = 'cancelled'. Two others have status = NULL — nobody recorded it.

SELECT COUNT(*) FROM orders WHERE status != 'cancelled'

How many rows come back?

A) 8 — nothing was excluded
B) 6 — the two cancelled orders were removed
C) 4 — the cancelled rows and the unknown-status rows
D) 2 — only the cancelled rows survive
1 min. Almost everyone says 6, and 6 is exactly what the query's author believed they were getting. This is the strongest single moment in the back half of the lecture — do not spoil it by hinting.

Answer: C — 4 Rows, and \$300 Gone

NULL != 'cancelled' evaluates to unknown, not true — and WHERE keeps only true. The two unknown-status rows were dropped silently.

They took \$300 of revenue with them — 30% of the table's total — out of a query whose author believed they were excluding cancellations. No error. No warning.

The Fix Is to Say What You Mean

What you wrote

WHERE status != 'cancelled'

kept |  total
-----+--------
   4 |  700.0

What you meant

WHERE status IS DISTINCT FROM 'cancelled'

kept |  total
-----+---------
   6 | 1000.0

IS DISTINCT FROM is != that treats NULL as an ordinary value rather than a contagion.

Six orders, \$1,000. Which is what you were asking for the whole time.

1 min. Give them the one-line rule: any time you filter on a column that could be NULL with != or <>, you are also silently filtering out the NULLs. If that is what you want, write it deliberately with OR status IS NULL. If it is not, use IS DISTINCT FROM.

 avg_skips_nulls | avg_over_all_rows
-----------------+-------------------
       160.71    |      140.63

COUNT(*) counts rows. COUNT(column) counts non-null values in that column. Two different questions, one keystroke apart.

AVG ignores nulls, so it divides by 7. The same sum over all 8 rows gives 140.63. A 14% difference from nothing but a disagreement about the denominator.

And neither number is wrong. They answer different questions: “average revenue among orders where we know the revenue” and “average revenue per order.”

2 min. Resist calling one of these a bug. The whole point is that both are correct answers to questions that differ by one word, and the analyst's job is knowing which one they asked. Go straight into the discussion.

Discussion: Which Average Do You Report?

\$160.71 or \$140.63 — which one goes in the report, and what do you need to know in order to choose?

 Chapter 1 gave you the vocabulary for this: MCAR, MAR, MNAR. Same problem, different syntax.

1 min think → 2 min share

3 min, press 3. Target: it depends on WHY the value is missing. If revenue is missing at random, AVG is fine. If revenue is missing precisely for the orders that were never invoiced, AVG silently drops the zero-revenue cases and OVERSTATES the average. The database cannot know which world you are in; you have to. Debrief line: "both numbers came out of the same eight rows and neither is a mistake — the mistake would be reporting one without knowing which question you answered."

Common Misconception

“Missing values show up as zeros or NaN, so I'll notice them.”

NULL is not zero and is not NaN. It is absent from arithmetic entirely. It does not shift a sum. It does not appear as an outlier. It does not raise an error.

It removes rows from filters and shrinks denominators in aggregates — and both happen without a warning.

Before trusting any aggregate: run COUNT(*) alongside COUNT(column) for every column you aggregate. If they differ, you have a decision to make — and making it deliberately is the whole job.

1 min. The COUNT(*) vs COUNT(column) habit is the single most portable thing in this section — it is two seconds of typing and it turns an invisible problem into a visible one. If you are running long, cut this slide and put the habit in the exit ticket instead.

Parquet: Storing by Column, Skipping What You Don't Need

Predicate pushdown — ask for WHERE year = 2024 and the engine skips any chunk whose metadata says it holds only 2019 data, without reading it.

Projection pushdown — ask for two columns out of forty and it reads two.

The Pattern to Internalise

Do the heavy work where the data is.
Bring back only the small result.

Filter, join and aggregate in SQL until the output is small enough to hold. Then call .df() and do your econometrics in pandas and statsmodels on a few thousand rows.

.df() is the boundary between the two worlds, and putting it as late as possible is most of what “working with large data” means in practice.

Misconception: “you need Spark for data bigger than RAM.” Clusters genuinely matter at some scale, but a columnar engine with pushdown streams and spills through files far larger than memory. Most economic data — including most administrative microdata you will ever touch — fits here. Reach for a cluster when you have measured that you need one.

Reading a Query You Did Not Write

You will read far more SQL than you write — from a colleague, a predecessor who has left, a dashboard nobody has audited in two years, or a language model. Six checks, index-card length.

1. Check the grain. COUNT(*) against COUNT(DISTINCT key). If they differ, you have fanout.

2. Check the row count against expectation. State what you expect first. “About 600 customers” is testable; “some rows” is not.

3. Check the joins. Is the right-hand table unique on the join key? If not, the join multiplies.

4. Check the filters against NULL. != 'cancelled' drops every NULL row — 30% of revenue in eight rows.

5. Check what it does not return. A customer dropped by an INNER that should have been LEFT; a month missing from a series, shifting every growth rate.

6. Compute one number by hand. Take one customer, work out their value, confirm the query agrees.

Check 5 is the failure mode most likely to survive review — because everything the query does return is correct.

2 min. Read checks 1 and 5 properly and let the others sit on the screen. Check 5 deserves the emphasis: a query returning plausible numbers about the WRONG POPULATION passes every sanity check anyone applies, because nothing in it is false.

Check 1, in Fifteen Seconds

SELECT COUNT(*)                    AS rows,
       COUNT(DISTINCT customer_id) AS distinct_customers,
       COUNT(*) * 1.0 / COUNT(DISTINCT customer_id) AS rows_per_customer
FROM fanned
 rows | distinct_customers | rows_per_customer
------+--------------------+-------------------
 4033 |                600 |              6.72

rows_per_customer is 6.72, not 1. That is the whole diagnosis.

Run it after every join you did not write yourself.

Discussion: Audit This Query

An LLM was given the customers / orders schema and asked for “average revenue per customer by region.” It returned:

SELECT c.region, COUNT(DISTINCT c.customer_id) AS customers,
       AVG(c.revenue) AS avg_revenue, SUM(o.order_value) AS total_orders
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.region

Exactly one of avg_revenue and total_orders is trustworthy. Which — and why is the other not?

2 min pairs → 2 min share

4 min, press 4. Target: total_orders is FINE — it sums a column that genuinely lives at the order grain, so one row per order is correct. avg_revenue is CORRUPT — c.revenue lives at the customer grain and is repeated once per order, so the average is order-weighted. COUNT(DISTINCT c.customer_id) is also correct, and that is what makes the query dangerous: a correct customer count sitting right beside a corrupted average, so the output looks internally consistent. Debrief line: "this query would pass code review at most companies." Optional live upgrade: ask a model for this in front of the class instead. Only do that if the room and the network are cooperating — the six checks are the content, not the source of the query.

Three Practices That Make LLM SQL Safe

Give it the schema, not just the question. Most hallucinated joins come from a model guessing at column names and relationships. Paste the DESCRIBE output of every table involved.

Ask it to state the grain. “What does one row of your result represent?” A model that cannot answer that has not thought about cardinality — and neither has its query.

Verify on a subset with a known answer. Ten hand-checked customers is enough — cardinality bugs and NULL bugs both show up at small scale.

The tool is fast and unreliable, so your job shifts from production to verification. That is not a downgrade — deciding whether an answer is correct has always been the harder and more valuable half.

Chapter 11 in a Nutshell

SQL and pandas implement the same relational algebra (Codd 1970). SQL is declarative — which is why its clauses execute in a different order than they are written.

There is no database. DuckDB resolves the table name out of your Python namespace, and .df() is the boundary back to pandas.

A join can silently multiply rows. Because every SE depends on $n$, a fanned-out join turns a null result into a significant one without changing a single underlying fact. Aggregate to the grain you want before you join.

Window functions aggregate without collapsing: LAG over a partition is groupby().shift(), and it is how you get growth rates, ranks and running totals on panels.

NULL is unknown, not zero. It removes rows from filters and shrinks denominators in aggregates — silently, in both directions.

Columnar formats with pushdown let you query files far larger than memory. Do the heavy work where the data is; bring back the small result.

You will read more SQL than you write, much of it machine-generated. Check the grain, the row count, the join cardinality, the NULL handling — and verify one number by hand.
